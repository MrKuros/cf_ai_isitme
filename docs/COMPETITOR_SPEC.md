# IsItMe: competitor-driven product spec

Written 2026-09-21 against the current tree (`src/lib/{probes,classify,radar,guard,explain}.ts`, `src/agents/{target-do,probe-do,user-agent,mcp}.ts`, `src/workflow/diagnose.ts`, `src/client/probe.ts`, `src/server.ts`).
Goal: match what competitors do well, avoid their known bugs (including ones **we already have**), and add what none of them offer.

Platform limits that shape every decision: Workers `fetch` only (no ICMP, UDP, traceroute, or address-family choice), `connect()` is blocked to Cloudflare IPs, no browser rendering, a Workers fetch exposes neither TLS cert details nor per-phase timings, and a no-cors browser fetch can't see status codes.

## 2. Pitfalls to avoid: design rules and acceptance tests

Each rule names the module that enforces it. Tests live in `test/*.test.ts` (vitest, fetch mocked) unless marked **[live]**, which means a manual smoke test against the public URL.

### R1. Bot protection is not an outage (new verdict `BLOCKED`)

- `httpProbe` reads status plus headers and at most the first 64 KB of the body on 403/429/503 (and 200, see R4). Add `ProbeResult.blocked?: "challenge" | "waf" | "rate_limit" | "geo"` and `server?`, `cfRay?`.
- Detection: `cf-mitigated: challenge` header; `server: cloudflare` with 403/503 and body `/Just a moment|cf-chl|challenge-platform/`; Akamai `server: AkamaiGHost` 403 "Access Denied"; DataDome `x-datadome` / `x-dd-b`; 429 counts as rate_limit; 451 counts as geo (legal block).
- A blocked probe is `ok: true` for reachability (the origin/edge answered), with `errorClass: "blocked"`.
- classify: if every server vantage that answered is `blocked` → verdict `BLOCKED` ("reachable, but it blocks automated checks; your browser result decides"). If the browser is also reachable, the confidence goes up. If the browser fails, fall through to user-side rules.
- Tests: (a) mocked 503, `server: cloudflare`, body "Just a moment..." → `BLOCKED`, not DOWN*\*; (b) 403 with `cf-mitigated: challenge` → `BLOCKED`; (c) plain 503 from `server: nginx` → DOWN*\*; (d) 429 → `BLOCKED` with signal "rate limited"; (e) **[live]** `httpbin.org/status/403` → not DOWN.

### R2. Slow is not dead

- Edge and ProbeDO: a first attempt with an 8 s timeout. On `timeout` or `connect`, **retry once** with 15 s. If the retry succeeds, the result is `ok` with `ms` from the retry and `retried: true`, and it feeds SLOW.
- Never compute any duration from a missing timestamp (`lastCheckedAt ?? null`, rendered as "never").
- Tests: (a) first call times out and the retry answers in 9 s → SLOW, not DOWN; (b) both time out → counted failed; (c) **[live]** `httpbin.org/delay/9` → SLOW; (d) `formatAgo(undefined)` returns "never", not "56 years".

### R3. TLS problems are their own layer (new verdict `TLS_ERROR`)

- Map a Workers subrequest status of 525/526, or TLS/cert error text, to `errorClass:"tls"`. Map 530 to `dns` (origin unresolvable). Keep 520–524 as `http_5xx` but add `cdnOrigin: true` when `cf-ray` is present ("Cloudflare's edge is fine, the site's origin server is failing").
- Verify empirically at build time which of these codes a Worker subrequest actually synthesizes versus the target zone's own response, and record it in `docs/SDK_NOTES.md`.
- classify: every answering server vantage fails with `tls` → `TLS_ERROR` ("server is up, certificate invalid, browsers will block it; only the site owner can fix it").
- Tests: (a) mocked 526 → TLS*ERROR; (b) **[live]** `expired.badssl.com` and `wrong.host.badssl.com` → TLS_ERROR; (c) mocked 522 with cf-ray → DOWN*\* with signal "origin server" (not TLS).

### R4. "200 but broken" (new verdict `PARTIAL`)

- On 2xx `text/html` with GET, read up to 64 KB: record `bytes`, `<title>`, and flags `empty` (<512 B of non-whitespace), `errorPage` (title/body matches `/(404|not found|error|service unavailable|bad gateway|maintenance)/i` on a 200), `parked` (`/domain (is )?for sale|parked|sedoparking|godaddy.*parked/i`).
- classify: all answering vantages report reachable, and a majority flag empty/errorPage/parked, or `expect` is missing → `PARTIAL` with the reason. `parked` is its own signal ("the domain is parked; the site is gone, not down").
- Tests: (a) 200 with a 40-byte body → PARTIAL; (b) 200 with `<title>502 Bad Gateway</title>` → PARTIAL; (c) a normal 30 KB page → HEALTHY; (d) `expect:"Sign in"` missing → PARTIAL "expected text not found".

### R5. Redirects, apex/www, and specific paths

- Follow up to 5 redirects manually. **Re-run `normalizeTarget` + DoH + `assertSafeTarget` on every hop** (SSRF). Record `chain: {url,status}[]`. The verdict is based on the final hop. Any 2xx/3xx/4xx on the final hop means reachable.
- If the user's URL has a path, also probe the origin root (one extra edge probe only): root OK plus path 404/410 → `PARTIAL` "the site is up; this page returns 404".
- If the apex fails at DNS/connect/TLS, probe `www.` (or strip `www.`) once at the edge, and add the signal "www.example.com works" plus a next step.
- Tests: (a) 301 → 200 → HEALTHY with a 2-hop chain; (b) 301 → dead host → DOWN\_\*; (c) 302 to `http://169.254.169.254/` → run refused with a guard error, never fetched; (d) 307/308 followed (not whitelisted away); (e) `/missing` → 404 with root 200 → PARTIAL; (f) apex NXDOMAIN, www resolves → signal present.

### R6. A platform failure is no data, not a vote

- `target-do.ts regions()`: a rejected RPC or thrown exception becomes `RegionProbe` with `noData: true`, which is excluded from every ratio. `classify` computes ratios only over vantages with `!noData`.
- ProbeDO runs a **control fetch** alongside every probe (`https://www.cloudflare.com/cdn-cgi/trace` plus one non-Cloudflare control, e.g. `https://www.google.com/generate_204`). If both controls fail, the result is `noData: true, vantageSick: true`.
- ProbeDO keeps a rolling 5-minute tally of distinct hosts it saw fail. If more than 50% of ≥6 distinct hosts are failing from this region while other regions see them fine, mark the region `vantageSick` for 5 min (the UptimeRobot EU / Pingdom datacenter lesson).
- The explanation lists missing vantages ("apac returned no data") instead of shrinking the denominator silently (Globalping MCP issue #51).
- Tests: (a) one ProbeDO rejects, 4 OK → HEALTHY, signal "apac: no data", confidence reduced, **not** DOWN_REGIONAL; (b) controls fail → noData; (c) a sick vantage's failures are excluded from watch alerts.

### R7. Quorum over distinct vantages

- Deduplicate vantages by `colo` before counting: two hints that landed in IAD count as one. Report the actual colo, never only the hint (the DO `locationHint` is only a hint).
- DOWN_GLOBAL needs **≥2 distinct colos failing** and ≥80% of answering vantages failing. With 1 failing colo and no other data, the verdict is `INCONCLUSIVE` (R12), not DOWN_GLOBAL.
- DOWN_REGIONAL needs ≥1 distinct colo failing **and** ≥1 succeeding, where the failing one isn't `vantageSick`.
- Signals always read "N/M regions (distinct colos) failed".
- Tests: (a) edge fails with regions=[] → INCONCLUSIVE; (b) 5 hints in 3 colos with 2 failing → counts as 2/3; (c) edge plus 4/5 regions fail across 4 colos → DOWN_GLOBAL.

### R8. Alerts: confirm, add hysteresis, one incident at a time

- A watch run that changes the verdict class (up = HEALTHY/SLOW/BLOCKED, down = DOWN\_\*/DNS_FAILURE/TLS_ERROR/UPSTREAM_OUTAGE/PARTIAL) does **not** alert. It schedules a confirm run in 60 s (`this.schedule(60, "checkWatch", …)`). The alert fires only if the confirm run agrees.
- Recovery needs 2 consecutive "up" runs (hysteresis). Moving within the same class (DOWN_REGIONAL → DOWN_GLOBAL) updates the open alert/incident and sends no new webhook.
- Suppress entirely when the change was caused by `vantageSick`/`noData` or by `INCONCLUSIVE`.
- `Watch` adds `pendingVerdict?`, `pendingCount?`, `openIncidentId?`.
- Tests: (a) HEALTHY → DOWN → HEALTHY on the confirm run → 0 alerts; (b) HEALTHY → DOWN → DOWN → 1 alert; (c) DOWN → HEALTHY → DOWN → no recovery alert; (d) DOWN_REGIONAL → DOWN_GLOBAL → 0 new webhooks; (e) HEALTHY → INCONCLUSIVE → 0 alerts.

### R9. Upstream/provider attribution needs strong evidence

- A BGP event counts only if: `confidence ≥ 8` (Radar scale), **and** it is ongoing or ended ≤2h ago, **and** one of its `prefixes` contains the target IP, **and** server vantages fail. Otherwise it's a context signal, not a verdict.
- Provider blame (N1) needs ≥3 distinct hosts on the same provider failing in 10 min, **or** the provider's own status page showing an incident. A single site failing on AWS is never an "AWS outage".
- Tests: (a) low-confidence hijack on AS13335 with the target failing → DOWN\_\*, not UPSTREAM; (b) a matching-prefix high-confidence leak within the window → UPSTREAM_OUTAGE; (c) an event ended 20h ago → ignored.

### R10. Only current Radar data drives verdicts

- `classify` uses outages/anomalies with `endDate == null` or `endDate` ≤ 2h ago. Older ones show only as "earlier today: …".
- Missing Radar data (`skipped`, errors, empty) never counts as "no outage"; the signal says "Radar: no data".
- Tests: (a) an outage that ended 10h ago with the browser failing → LIKELY_YOUR_NETWORK, not ISP_OUTAGE; (b) an ongoing ASN outage → ISP_OUTAGE; (c) radar skipped → no "No Radar outages" line.

### R11. Separate resolver failures from domain failures

- `dohLookup(host, {resolver})`, with resolvers `cloudflare` (`cloudflare-dns.com/dns-query`) and `google` (`dns.google/resolve`, same JSON shape). The edge queries both in parallel.
- DNSSEC: on SERVFAIL, re-query with `cd=1`. SERVFAIL with CD off plus NOERROR with CD on means **DNSSEC validation failure** ("breaks on validating resolvers only", the Slack 2021 case).
- Verdict logic: both resolvers fail with the same rcode → DNS_FAILURE (the domain's problem). Only one fails → not DNS_FAILURE, signal "resolver X failing" (and if X is 1.1.1.1, raise the self-suspect flag, R18).
- Browser: DoH to **both** resolvers. Both fail while the control is reachable → "your network blocks DNS-over-HTTPS / public resolvers". The target unreachable while browser DoH resolves and edge OK → "likely your local DNS resolver or filter" (the local resolver can't be read directly; say it is inferred).
- Tests: (a) CF DoH times out, Google OK → no DNS_FAILURE; (b) SERVFAIL, then NOERROR with cd=1 → DNS_FAILURE subtype `dnssec`; (c) **[live]** `dnssec-failed.org` → dnssec subtype; (d) **[live]** a random nonexistent domain → NXDOMAIN, no duration text.

### R12. An honest "we don't know" (new verdict `INCONCLUSIVE`)

- Emitted when fewer than 2 distinct answering server vantages exist and the browser is missing or agrees with nothing, or when all server vantages are noData.
- It replaces the current `DOWN_GLOBAL 0.5` / `HEALTHY 0.5` fallbacks (B7).
- Tests: (a) all regions noData, edge null, browser failed → INCONCLUSIVE; (b) the same with browser OK → INCONCLUSIVE with "your browser could reach it".

### R13. The LLM explains, it never decides

- Existing rule kept: the verdict is final. Added: the prompt gets `signals[]` and must only restate them. It must not name a provider, ISP, or cause unless the string appears in the evidence. If Workers AI fails, the UI renders `signals` plus a templated next-steps list per verdict (in `explain.ts`, keyed by verdict and subtype).
- Test: a stubbed AI returning text that mentions "AWS" when the evidence has no AWS → the post-filter drops the sentence (a simple provider-name check against the evidence JSON).

### R14. Crowd data only corroborates

- Crowd checks come only from measured probes (browser/edge), never a click. They can move confidence by at most ±0.1 and can never on their own flip HEALTHY to DOWN.
- Geography shows failing/total per ASN/country, and only for buckets with ≥3 samples.
- Tests: (a) 20 failing crowd checks from other ASNs with all server vantages OK → HEALTHY (signal mentions the crowd); (b) a bucket with 2 samples is not shown.

### R15. Untrusted client input is labelled and validated

- `/api/extra-check` and `submitBrowserProbe` validate the `BrowserProbe` shape (types, lengths, `ms` 0–60000, `dns` sub-shape) and cap strings. Reports render visitor checks as "self-reported by a visitor on AS#### (ISP)".
- Test: a malformed `browser` (string fields where a boolean is expected, 10 KB error) → 400.

### R16. Agent/API-friendly contract

- `GET /api/v1/check?url=&wait=1` (default) keeps working. `wait=0` returns `{runId, host, pollPath}` at once, and `GET /api/v1/runs/:id` polls. Each API/MCP caller gets its own agent key (`api:<hash(ip)>`), not `smoketest_device_0002` (B13).
- Documented, stable verdict enum plus subtype in `docs/API.md`. MCP returns `CheckOutcome` (summary) by default. `get_report(host,id)` returns full evidence. Tool schemas import the same zod schemas used by the REST handler (prevents Globalping-style drift).
- Tests: (a) `wait=0` → 202 with runId, then polling returns the verdict; (b) the MCP tool list matches the REST schema snapshot.

### R17. Stated retention and graceful expiry

- Reports are kept 30 days (a TargetDO alarm deletes older rows). `/r/:host/:id` for a missing report renders "This report expired (reports are kept 30 days)", not a broken page. The API returns 410.
- Test: a report older than 30 days → 410 plus an "expired" UI state.

### R18. Shared fate: say when Cloudflare is the suspect

- `Evidence.selfSuspect` is set when any of these hold: the Cloudflare status summary (`https://www.cloudflarestatus.com/api/v2/summary.json`, cached 60 s) shows a non-operational component; `target` is behind Cloudflare (cf-ray / ASN 13335) **and** failures are Cloudflare-generated (5xx with `server: cloudflare` and no origin 52x) across ≥2 colos; 1.1.1.1 DoH fails while Google DoH works.
- UI banner: "IsItMe runs on Cloudflare too. Treat this result with care." Explanation step lists it.
- Browser probe results render on the client even if the Worker run fails (the probe already runs client-side, so the UI shows its own result when the websocket/run errors).
- Test: mocked cloudflarestatus "major_outage" → banner flag set and confidence capped at 0.7.

### R19. SSRF, abuse, and rate limits (kept, extended)

- Existing guard plus: re-guard on every redirect hop (R5); watch intervals ≥5 min; at most 10 watches per device; badge and report endpoints never trigger probes (they read the cache only). Known ceiling: DNS rebinding (`ponytail:` marked).
- Test: (a) a badge request with no cached result → "unknown" SVG, zero fetches; (b) the 11th watch → error.
